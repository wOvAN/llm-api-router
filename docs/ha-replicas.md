# Отказоустойчивая работа нескольких реплик роутера

Заметка по дизайну: что мешает запускать несколько реплик `llm-api-router`
параллельно за балансировщиком, и какие есть варианты это закрыть.

Состояние сессии отсутствует: каждый запрос самодостаточен, sticky-сессии не
нужны. Все проблемы — это разобщённое (per-process) управляющее состояние.

## 1. Инвентарь состояния

Всё состояние создаётся в `main.go:59-84` и живёт в памяти процесса.

| Состояние | Где | Проблема с N репликами |
|---|---|---|
| config | `config/store.go` — файл + память | Запись `os.WriteFile` выполняется под **локальным** mutex (`config/store.go:90`). Общий bind-mount: last-writer-wins, возможен интерливинг и испорченный файл. Правка на реплике A не видна реплике B, пока вручную не дёрнуть `POST /admin/api/config/reload` |
| RateLimiter | `config/ratelimit.go` | Счётчики локальные: правило «5 фейлов за 60s» фактически превращается в 5×N фейлов, кулдауны рассинхронизированы между репликами |
| QuotaTracker (TPM/RPM) | `config/quota.go` | Скользящее окно локальное → лимиты превышаются примерно в N раз. Резервация in-flight бюджета (`DeclaredOutputBudget`) тоже локальная. Самый острый пункт |
| HealthTracker | `config/health.go` | Локальные пинги `/v1/models`. Скорее фича, чем баг: независимый вид на бэкенд. Минусы — N× проб и разные решения у разных реплик |
| metrics | `metrics/metrics.go` | Ring buffer на 100 запросов + суммы per-replica. GUI через балансировщик попадает на случайную реплику и видит частичную картину |
| Active requests | `metrics` `IncrActive` | Локальный счётчик, суммируется только снаружи |

## 2. Варианты

### Вариант 0. Stateless-lite (конфиг read-only)

Реплики только роутят трафик. Конфиг приходит извне (том только на чтение,
ConfigMap), запись через admin-API запрещена (`ADMIN_READONLY`). GUI и edits —
через одну выделенную реплику или вовсе оффлайн: `example.config.json` в git,
доставка конфигов внешним механизмом, применение по SIGHUP или по
`POST /admin/api/config/reload`.

- RateLimiter/Quota: пороги делятся на N (`threshold/N`, `tpm_limit/N`) —
  деградация предсказуемая
- Health: локальные пинги как есть
- Нужно: env-флаг, запрещающий записи, и авто-reload при изменении файла
  (goroutine, сравнение mtime раз в 5s — внешних зависимостей не требует)
- Объём работы: ~50 строк
- Честно работает, пока конфиг меняется редко и есть внешний источник истины

### Вариант 1. Конфиг через peer-sync, состояние остаётся локальным

Полностью на stdlib. Конфигу добавляется ревизия (хэш сериализованного
`domain.Config`), хранится рядом с самим конфигом.

- `GET /admin/api/config/rev` — дешёвый эндпоинт для сравнения ревизий
- Каждая реплика опрашивает пиеров раз в 2-3s; если хэш разошёлся — `Load()`.
  Альтернатива push: реплика, сделавшая запись, шлёт `POST /admin/api/config/reload`
  по списку пиров (`ROUTER_PEERS=http://r2:8080,http://r3:8080`)
- Метрики для GUI: fan-out по `peers` и слияние суммарий, либо GUI sticky на
  одну реплику
- `flock` на `save()` обязателен при любом варианте с общим томом
  (`syscall.Flock`, stdlib)
- Объём работы: ~150-250 строк, ноль новых зависимостей
- Остаётся нерешённым: RateLimiter и Quota по-прежнему локальные, то есть
  N× overspend по TPM

### Вариант 2. Redis только для горячего состояния (рекомендуется, если лимиты важны)

Конфиг — как в варианте 1 (файл + rev-sync). Наружу уходит только то, что
обязано быть общим:

- RateLimiter: `INCR` + `EXPIRE` по ключу server-id
- QuotaTracker: ZSET скользящего окна плюс атомарная резервация
  (Lua-скрипт или `WATCH`), с TTL на резервации, чтобы убитая реплика не держала
  бюджет вечно
- Health остаётся локальным (децентрализованный вид корректнее), metrics
  локальные с лейблом `instance`, суммирование на стороне Prometheus

Минус: ломает правило «одна внешняя зависимость» (`golang.org/x/net`).
Выход — `QuotaStore`/`FailStore` interface с in-memory реализацией по умолчанию
и Redis-бэкендом, включаемым только когда в конфиге заданы
`tpm_limit`/`rpm_limit` (или за build tag).
Объём работы: ~300-400 строк вместе с тестами.

### Вариант 3. Общий store как источник истины (Redis / etcd / Postgres KV)

Конфиг тоже снаружи, файл становится кэшем или экспортным артефактом. Реплики
подписаны на изменения (etcd watch, Postgres LISTEN). Общие RateLimiter, Quota и
metrics.

- Решает всё, включая честный GUI с полной картиной
- Самый дорогой по времени, плюс отдельный вопрос: где лежат API-ключи
- Оправдан при 5+ репликах или когда нужен один GUI с полными метриками

### Вариант 4. Shard-by-rule (consistent hashing между репликами)

Каждое правило и каждый серверный лимит имеют реплику-владельца; чужие запросы
форвардятся владельцу. Даёт точные TPM/RPM без внешней БД.

- Требует membership/выборов лидера и форвардинга SSE-трафика между пиерами
- Оверкилл для текущего размера проекта; держать как потолок на случай
  «Redis тоже не хотим»

## 3. Слой балансировки (важнее, чем кажется, независим от выбранного варианта)

- Долгие таймауты и отсутствие буферизации для `text/event-stream`. Существующие
  heartbeat'ы (`keepAliveWriter`, `waitSignalWriter`) спасают от клиентских
  idle-таймаутов, но буферизация на LB ломает покадровую выдачу
- **Запретить ретраи POST на уровне LB.** Chat-запрос не идемпотентен: повтор
  балансировщика после оборванной стрима даёт двойную генерацию и двойную
  оплату. Ретраи уже реализованы внутри роутера (`X-Router-Retries`)
- Graceful shutdown сейчас 10s (`main.go:155`) — мало для стрима длиной в минуты.
  Либо LB сам выводит реплику из пула и ждёт окончания (preStop + draining
  timeout), либо добавить `/readyz` в состоянии «новые запросы не принимаю» и
  увеличить drain

## 4. Порядок работ

1. `flock` в `store.save()` — нужен при любом варианте: общий том без него это
   риск испорченного `config.json`
2. Вариант 1: rev-хэш плюс peer reload. Дёшево и закрывает единственную реально
   болезненную рассинхронизацию — конфигурацию
3. Вариант 2 через interface `QuotaStore` с in-memory дефолтом — Redis
   подключать только когда включены `tpm_limit`/`rpm_limit`
4. RateLimiter, Health и metrics оставить локальными, осознанно разделив пороги
   на N. Это дешевле, чем синхронизировать их

## 5. Что сознательно не делаем

- Gossip-обмен счётчиками между пиерами (собственный mini-CRDT)
- Election лидера с форвардингом запросов ему

Возвращаться к ним стоит, только если посчитать, что N× деградация лимитов
дороже ~400 строк Redis-бэкенда.
